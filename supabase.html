O que é um BaaS?

Backend como serviço (BaaS) reúne recursos de servidor prontos para uma aplicação. O Supabase oferece PostgreSQL gerenciado, autenticação e armazenamento de arquivos (Storage), acessíveis por APIs e bibliotecas JavaScript no navegador, conforme as permissões configuradas.

O banco continua relacional: tabelas, colunas, chaves e SQL fazem parte do modelo. O serviço cuida da infraestrutura, enquanto você define os dados, as regras de acesso e a aplicação.

Área de usuários, sessões e provedores de login. Autenticar identifica quem está acessando; autorizar determina o que essa pessoa pode fazer.

Referência para localizar a URL e as configurações da API. As chaves ficam em Settings → API Keys na interface atual. Os rótulos podem variar; não copie segredos para o frontend.

Chaves e segurança

anon key: chave legada pública por design, utilizável no navegador. Não é uma senha de administrador e não identifica o usuário. O acesso depende dos privilégios concedidos aos papéis e das políticas de Row Level Security (RLS) configuradas nas tabelas expostas.

service_role key: chave legada privilegiada que pode ignorar RLS. NUNCA deve aparecer no frontend, em páginas HTML ou no repositório. Seu uso pertence exclusivamente a ambientes de servidor confiáveis.

Nos projetos atuais, prefira as chaves publishable para clientes públicos e secret apenas no servidor. Elas substituem os tipos legados anon e service_role. A separação entre acesso público e privilegiado continua essencial.

É o mesmo princípio do menor privilégio do guia MongoDB: cada aplicação recebe apenas o acesso necessário. No navegador, variáveis de ambiente incorporadas ao build também ficam visíveis.

Row Level Security: acesso por linha

RLS aplica políticas do PostgreSQL para decidir quais linhas cada papel pode consultar ou alterar. Uma chave pública só é adequada quando as permissões e as políticas limitam o acesso aos dados pretendidos.

Exemplo conceitual: numa tabela de anotações, cada linha possui o identificador de seu proprietário. Uma policy de leitura para usuários autenticados permite consultar somente linhas cujo proprietário corresponde ao usuário da sessão. Inserir, atualizar e excluir exigem políticas próprias; esconder um botão na tela não protege o banco.

Com RLS habilitada, sem uma policy que permita o acesso, a API com chave pública não recebe autorização para ler as linhas. Chaves privilegiadas podem contornar essa proteção.
