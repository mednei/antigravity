O que é MongoDB?

MongoDB é um banco NoSQL orientado a documentos. Armazena dados em BSON, uma representação binária semelhante ao JSON que também suporta tipos como datas. Documentos são agrupados em coleções e podem conter campos, listas e objetos aninhados.

O modelo documental é útil quando os dados de uma entidade são lidos juntos e sua estrutura pode evoluir. SQL costuma ser uma boa escolha para dados relacionais com restrições e consultas entre várias tabelas. A decisão depende das relações, consultas e regras de integridade; ambos exigem modelagem.

Correspondências para orientar a leitura, sem equivalência exata

Três ferramentas, papéis diferentes

Atlas

Serviço gerenciado na nuvem para hospedar o banco e configurar usuários, permissões e acesso de rede.

Compass

Aplicativo de inspeção visual para explorar coleções, consultar documentos e analisar a estrutura dos dados.

mongosh

Shell interativo para consultar e administrar o banco por comandos. Exige as permissões do usuário conectado.

Segurança de Credenciais

Nunca escreva a connection string com senha diretamente no código. A expressão “senha master” serve de alerta: uma URI contém as credenciais de um usuário de banco, cujos privilégios precisam ser limitados. Nunca use o administrador na aplicação.

Mantenha o segredo fora do projeto

Guarde o arquivo .env fora da pasta do projeto, por exemplo em D:\projetos\credenciais\mongodb.env. Se ficar dentro, inclua-o no .gitignore antes do primeiro commit. Não copie o arquivo para pastas públicas, builds ou mensagens de IA.

Arquivo mongodb.env externo — exemplo ilustrativo

MONGO_URI="mongodb+srv://usuario:SENHA@cluster0.xxxxx.mongodb.net/meubanco"

Em um backend Node.js com o pacote dotenv instalado, o carregamento pode ser feito assim:

Carregamento no backend Node.js

require('dotenv').config({ path: 'D:/projetos/credenciais/mongodb.env' });
// process.env.MONGO_URI disponível; mantenha o arquivo externo fora do Git

process.env.MONGO_URI fica disponível no processo do servidor. Este trecho é apenas material de estudo: o site não carrega arquivos de ambiente nem abre conexões. Um arquivo externo reduz o risco de versionamento, mas não protege contra cópia manual, logs ou exposição no frontend.

O .gitignore não apaga o passado

Aviso crítico: se o .env já foi commitado, adicioná-lo ao .gitignore não o desversiona. O comando abaixo remove o arquivo do índice, mantendo a cópia local; a remoção deve ser registrada no próximo commit.

Remover .env do índice do Git

git rm --cached .env

O histórico do Git mantém versões anteriores. Se já houve push, troque a senha imediatamente. Remover o arquivo do commit atual não revoga a credencial nem elimina cópias do histórico.

Conceda apenas o acesso necessário

No Atlas, crie um usuário específico por aplicação em Database Access (na interface atual, Database & Network Access → Database Users). Dê somente as permissões necessárias ao banco utilizado. A conta de acesso ao painel Atlas é diferente do usuário do banco.

Em Network Access / lista de IPs, permita somente as origens necessárias. Evite liberar a internet inteira com 0.0.0.0/0.

Se houver vazamento

Troque a senha, revogue credenciais e acessos comprometidos e atualize os ambientes autorizados. Revise registros de acesso e o histórico do repositório para identificar a exposição. Trate a limpeza do histórico como medida adicional: a rotação do segredo é imediata.

Checklist de segurança

  • Guardar o arquivo de credenciais fora da pasta do projeto.
  • Configurar o .gitignore antes do primeiro commit e conferir os arquivos preparados.
  • Criar um usuário de banco por aplicação com o menor privilégio.
  • Restringir a lista de IPs às origens necessárias.
  • Manter segredos fora do frontend, dos logs e das mensagens de IA.
  • Trocar senhas expostas, revogar acessos e revisar o histórico.
